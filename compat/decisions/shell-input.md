# Shell input: find in page, drag and drop, single instance, tab close and reorder

Status: **proposed — requires Task 8 approval**

Scope: `crates/marknexia-win32` (`find.rs`, `dragdrop.rs`, `single_instance.rs`, `window/input.rs`, the tab-strip parts of `accessibility.rs`) and `crates/marknexia-webview` (`protocol.rs` find messages, `find_adapter.js`, `ShellAccelerator`). The .NET sources are `src/Marknexia.App/MainWindow.Search.cs`, `MainWindow.xaml.cs` (`Root_DragOver`, `Root_Drop`, `OpenRepositoryFolderAsync`, tab close and reorder, `SelectAdjacentTab`, keyboard accelerators), `App.xaml.cs` (single instance and activation) and `src/Marknexia.Core/StartupFileResolver.cs`.

Evidence class: implemented, compiled and headless-tested; the review fixes of 2026-11-06 (activation gating and worker thread, integrity and AppContainer checks, deferred UIA close, 44-DIP close buttons, high-contrast tab text, origin-bound adapter, message tokens, shutdown) are in the same class. The native gates in `crates/marknexia-win32/tests/native_input.rs` have not run yet (the workstation was locked); they need CI or an unlocked desktop. Items marked *unverified* describe .NET behavior that was read from the source or the WinUI defaults, not observed.

## Parity that holds

* **Find:** the per-tab `DocumentSearchState` rules (request ids, stale and mismatched results ignored, results stored for inactive tabs), the count texts (empty, `No matches`, `<n> of <m>`), `Document loading…` before the document is ready, the diagnostic `Find is temporarily unavailable. Wait for the document to load and try again.`, Ctrl+F, the toolbar button `Find in document` and View > Find in document toggle the bar, Escape closes it (hide, clear the box, store an empty result, clear the page selection), Enter and Shift+Enter in the box, the re-run of the active tab's search when its document finishes loading with the bar visible, and the page-side search itself: the unchanged .NET `bridge.js` `findText` and `clearSearch` do the work.
* **Drop:** only the first item counts; a Markdown file (`.md`, `.markdown`, `.mdown`, `.mkdn`, case-insensitive) opens in a tab; a folder becomes the repository root and its `README.md` opens when it exists; any other file shows `Marknexia opens Markdown files (.md, .markdown, .mdown, .mkdn).`; the drop effect is copy.
* **Single instance:** one running instance per key (`Marknexia.SingleInstance`); a later launch hands its command line over and exits; the running instance does `BringToFront` exactly (`ShowWindow(SW_RESTORE)`, which also restores a maximized window, then `SetForegroundWindow`) and opens `StartupFileResolver.FindFirstExisting` of the sender's arguments followed by its own startup arguments (the .NET `Environment.GetCommandLineArgs().Skip(1)` fallback is kept). File-association activation arrives as a command line and takes the same path. Drops and activations open through the chrome's open path (`chrome::open_or_select`, .NET `OpenDocumentInTabAsync`: the file check with `File not found: …`, an already open path (ordinal, case-insensitive) selects its tab, recent files, repository detection), and a dropped folder through `chrome::open_repository` (.NET `OpenRepositoryFolderAsync`: tree, recent folders, saved root, sidebar switched to the repository view, `README.md`). `open_document` also selects an already open tab, so the Open dialog behaves the same.
* **Tabs:** closing the active tab selects the tab that takes its index, else the new last tab; closing an inactive tab keeps the selection; Ctrl+W, Ctrl+Tab and Ctrl+Shift+Tab are unchanged; drag reorder changes the visual order, which is also the Ctrl+Tab order; a middle click closes a tab (WinUI `TabViewItem`, *unverified*).

## Observable differences

| ID | Condition | .NET oracle | Rust target |
| --- | --- | --- | --- |
| FIND-1 | F3 and Shift+F3 | No accelerator. | Find next and find previous. With the bar hidden, the bar opens first (restoring the tab's query), then the search runs. |
| FIND-2 | Ctrl+F, F3, Shift+F3 or Escape while the document (WebView2) has keyboard focus | *Unverified.* The root `KeyboardAccelerator`s may not fire inside WebView2; its default Ctrl+F opens the Edge find bar. | Ctrl+F, F3 and Shift+F3 leave the page and drive the shell find bar; WebView2's own find bar never opens. Escape stays with the page (it leaves an expanded Mermaid diagram), so it closes the find bar only when focus is in the shell. |
| FIND-3 | Query length | Unlimited `TextBox`. | At most 1,024 UTF-16 units (`EM_LIMITTEXT`, `MAX_FIND_QUERY_UNITS`); the bridge refuses longer queries in both directions. |
| FIND-4 | The page reports an inconsistent result (position past the count, no position with matches, matches for an empty query) | `TryApplyRenderedResult` throws `ArgumentOutOfRangeException`, caught as `ArgumentException`: the count clears and the diagnostic shows. | The bridge rejects the message (`InvalidPayload`); also a count above 1,000,000. The request stays pending; no diagnostic. |
| FIND-5 | Transport | `ExecuteScriptAsync("window.marknexiaBridge?.findText(...)")` and its JSON result. | Typed, versioned messages (`find`, `clearFind`; `findResult`, `findUnavailable`) bound to protocol 1, the tab and the document epoch, through a host-injected adapter (`AddScriptToExecuteOnDocumentCreated`). The rendered page bytes and `bridge.js` stay identical to .NET. A thrown or missing `findText` reports `findUnavailable`, shown as `Document loading…` (.NET: a `null` script result, the same text). |
| FIND-6 | The find box text is restored on a tab switch | *Unverified.* Setting `SearchInputBox.Text` raises `TextChanged`, which clears the count. | The restored count stays visible (the shell's own text change is not user input). |
| FIND-7 | Find bar visuals | `TextBox` with placeholder `Find in document...`, glyph buttons. | A visible `Find in document` label before the box (it is the box's accessible name), line-drawn chevron and cross buttons with the .NET accessible names. |
| DROP-1 | A drop over the document area | *Unverified* whether WinUI routes a drop over the WebView2 to `Root_Drop`. | The shell window accepts `CF_HDROP` (`WM_DROPFILES`); a drop over the document goes to WebView2, which cannot navigate away from the pinned document, so nothing opens. |
| DROP-2 | The dropped path fails the document path gate (device namespace, pipe, relative, `..`, reserved name, stream, and so on) | No gate. | Nothing opens; the status shows `Marknexia cannot open items from this location.` |
| SI-1 | Mechanism and trust | `AppInstance.FindOrRegisterForKey` and `RedirectActivationToAsync`. | Named mutex `Local\<key>.<user SID>` and a message-mode named pipe `\\.\pipe\<key>.<user SID>.<session>`: one instance, local clients only, DACL for the current user only, identification-only client QoS. Both ends verify that the other process runs as the same user in the same session, at an integrity level at least their own, and not in an AppContainer, so a sandboxed or lower-integrity process of the same user that pre-creates the pipe name is never trusted. A first instance whose pipe name is already held reports `Files opened from other launches cannot reach this window; they open in their own windows.` and releases its mutex, so later launches start their own windows instead of handing off to that name. An elevated first instance refuses a non-elevated sender, which then opens its own window after the retry period (SI-3). One message: `MNXA`, version 1, the sender's working directory and its unsplit arguments, at most 32,767 UTF-16 units each, exact framing, valid UTF-16 without NUL, read with a 2-second timeout, acknowledged. Anything else is dropped. |
| SI-2 | A relative path in a later launch | Resolved against the running instance's current directory (`Path.GetFullPath` runs there). | Resolved against the later launch's working directory. A root-relative path keeps that launch's drive. |
| SI-3 | The running instance does not answer (still starting, shutting down, or refusing the sender) | `RedirectActivationToAsync` fails; the exception is logged and rethrown, so the later launch crashes. | The later launch retries for 5 seconds, then runs as an independent instance. A name held by another user's object also gives an independent instance. |
| SI-4 | `MARKNEXIA_INSTANCE_KEY` (1–64 of `A–Z a–z 0–9 . _ -`) | No equivalent. | Replaces the key, so test and measurement launches never hand off to each other or to a user's shell. |
| SI-5 | Activation candidates and the file system | `File.Exists` and `Path.GetFullPath` on every candidate, on the UI thread. | Every candidate is made absolute lexically, then passes the document path gate before any file-system call (`GatedProbe`): before the existence check, before 8.3 expansion (`GetLongPathNameW`), and again on the expanded path. The existence check opens with identification-only QoS. Resolution runs on a worker thread; the window comes to the front at once and the file opens when the result is posted back. A sender with more than 64 arguments is ignored (the running instance's own arguments are still tried, at most 64). A refused path opens nothing; the status shows the drop refusal text. |
| SI-6 | The first instance's own command line | `StartupFileResolver` opens the first existing Markdown file only. | Unchanged from the earlier Rust shell: every path argument opens (`documents::startup_paths`). Only hand-off uses `StartupFileResolver`, with the Win32 short-name expansion (SET-8c). |
| TAB-1 | Close buttons | `CloseButtonOverlayMode="OnPointerOver"`: on the selected tab and on hover. | Painted on every tab, a square of the strip height (44 DIP) at the slot's right edge; no hover or pressed visual. A press and release on the same close button closes. A slot narrower than two 44-DIP targets has no close button: it is not painted or hit, and its UIA button reports `IsOffscreen` with an empty rectangle (Invoke still closes the tab; a middle click and Ctrl+W still work). The geometry is headless-tested at 96, 144 and 192 DPI; above 96 DPI it is not native-tested. |
| TAB-2 | UIA close affordance | WinUI `TabViewItem` close button (*unverified*: name `Close Tab`, Invoke). | Each `TabItem` has one child: a `Button` named `Close Tab` with the Invoke pattern, not keyboard focusable. Invoke queues the close and returns; the close runs on the next message-loop turn (WebView2 rejects COM inside the UIA call), then `ChildrenInvalidated` is raised on the tab control. |
| TAB-3 | Drag reorder | `CanReorderTabs`, WinUI drag visuals. | Past the system drag distance (`SM_CXDRAG`) the pressed tab moves live to the slot under the pointer; each move raises `ChildrenReordered` on the tab control. No tear-out (as .NET). |
| TAB-4 | Ctrl+W when the WebView session is in use by an outer call | Not applicable. | The close is refused (the key is not handled) rather than closing a tab whose document cannot be removed. A UIA Invoke close that arrives then is kept and runs once the session is checked back in (the next poll). |
| TAB-5 | The active tab in high contrast | System colors. | `ButtonText` on `ButtonFace` (the accent `Highlight` is not used on the `ButtonFace` fill). |
| MSG-1 | Window messages from other processes | Not applicable (WinUI). | Any process at the same or a higher integrity level can post to the shell window (UIPI blocks lower levels). The shell's private messages (`WM_APP + 0x100` to `0x103`) carry a per-process random token in `lparam` and are ignored without it; they only make the shell drain its own queues, and a close names a tab that must exist. `WM_DROPFILES` is used only when its handle is a global memory block of this process with a plausible `DROPFILES` header; otherwise it is ignored and never released. A same-integrity process of the same user can still post a well-formed drop of its own; that is inside the user's trust boundary. |
| SHUT-1 | A later launch during shutdown | Not applicable. | From `WM_DESTROY` the server acknowledges nothing, so the sender retries and opens its own window. An activation acknowledged just before shutdown, but not yet opened, is lost. |
| FIND-8 | The injected find adapter | Not applicable. | It is bound to the pinned document's origin (passed as JSON data) and stays inert in any other origin or in a frame. |

## Rollback

No setting, file or registry value is written by these features. Removing the hooks in `window.rs` restores the earlier shell; the named mutex and pipe exist only while an instance runs.
