# Link navigation between documents

Status: **proposed — requires Task 8 approval**

Scope: `crates/marknexia-webview` (`link_adapter.js`, `protocol.rs` link messages, `host.rs` `rebind_document`, `callbacks.rs` document slot and navigation ids, `session.rs` `replace_document`), `crates/marknexia-navigation` (`FileProbe`, `AssumeExists`) and `crates/marknexia-win32` (`window/chrome/links.rs`, `chrome_model.rs` link model and `TabLocation`, `documents.rs` `probe_document_file`, `window/shell_ops.rs` `open_external`). The .NET sources are `src/Marknexia.App/MainWindow.xaml.cs` (`CoreWebView2_WebMessageReceived`, `HandleLinkClick`, `OpenDocumentInTabAsync`, `OpenDocumentInTabCoreAsync`, `ReplaceActiveDocumentAsync`, `ApplyPendingLocationAsync`, `Back_Click`, `Forward_Click`) and `src/Marknexia.Navigation/NavigationResolver.cs`, `NavigationHistoryManager.cs`.

Evidence class: implemented, compiled and tested. Headless: `crates/marknexia-win32/tests/link_navigation.rs` (every v1 navigation fixture class routed to its action, the wiki model, hover text, fallback mapping, history with scroll offsets), `crates/marknexia-webview/tests/protocol.rs` and `rendered_document.rs` (message shapes and validation, adapter binding, `bridge.js` unchanged). Native: `marknexia-webview` `session::native_tests::native_replace_document_reuses_the_controller` and the `uia-native-links` gate (`crates/marknexia-win32/tests/native_links.rs`). Items marked *unverified* describe .NET behavior read from the source or from WebView2 defaults, not observed.

## Root cause of the reported bug

The frozen .NET `bridge.js` intercepts link clicks and posts an untyped `{type:'openLink', href}`. The Rust protocol accepts only typed, identity-bound messages, so every click was dropped; nothing in the shell routed `OpenLink` either.

## Parity that holds

* **Resolution:** `marknexia-navigation` resolves the raw `href` attribute exactly as .NET `NavigationResolver` (v1 fixtures; NAV-1 to NAV-4 apply): anchor-only, relative (`./`, `../`), repository-root (`/`), absolute and `file:` paths, percent-decoding once, the sandbox check before any probe, external `http:`/`https:`/`mailto:`/`ftp:`/`tel:` under `AllowExternalLinks`, and `javascript:`/`vbscript:`/`data:` blocked. The context is the active tab's file and its repository root (.NET `ResolveRepositoryRootForDocument`: the open repository when it contains the document, else the detected one), with the `EnforceRepositorySandbox` and `AllowExternalLinks` settings.
* **Actions (.NET `HandleLinkClick`):** `SameDocumentAnchor` scrolls the document and records the previous location when the anchor changes; `CrossDocument` and `CrossDocumentWithAnchor` show the target in the **same tab** (`reuseActiveTab: true`, `ReplaceActiveDocumentAsync`) even when another tab shows it, push the previous location (which clears forward), rename the tab to the file name, replace the outline, add the file to the recent files, set the repository when none is open, and scroll to the anchor after the load (`ApplyPendingLocationAsync`); `BrokenTarget` shows the resolver's message as a warning (fallback `Broken link or missing target file.`); `BlockedOrInvalid` shows it as an error (fallback `Blocked unsafe link destination.`).
* **Messages:** `Target file not found: <path>`, `Repository-relative file not found: <path>`, `Absolute target file not found: <path>`, `Access blocked: …`, `External links are disabled by policy.`, `Unsupported or unsafe protocol.`, and `Unable to open document: <error>` when the target cannot be shown.
* **Folder links:** `folder/` is a missing file (`File.Exists`), as in .NET; no `README.md` or `index.md` is opened.
* **Other files in the repository:** any existing file opens as a document in the same tab, as in .NET (no reveal, no default application).
* **Ctrl, Shift and Alt clicks** follow the link like a plain click (the .NET bridge ignores modifiers). Enter on a focused link raises the same click.
* **History:** per tab, back and forward stacks with .NET `NavigationHistoryManager` semantics; Back, Forward, Alt+Left and Alt+Right.
* **No confirmation** before an external link is handed to the system, as .NET `Launcher.LaunchUriAsync`.

## Observable differences

| ID | Condition | .NET oracle | Rust target |
| --- | --- | --- | --- |
| LNK-1 | Transport of a link click | `bridge.js` posts `{type:'openLink', href}`; `CoreWebView2_WebMessageReceived` reads it from any page. | This lane does not change `bridge.js` (its link handler is the .NET one; other lanes record their patches as parity-asset-patch blocks). A host-injected link adapter (`AddScriptToExecuteOnDocumentCreated`, origin-bound, bound to the tab id and document epoch) takes primary clicks on `a[href]` in the capture phase on the window, before `bridge.js`'s body listener, calls `preventDefault` and `stopImmediatePropagation`, and posts the typed `openLink` (protocol 1, tab, epoch, raw `href`, at most 8 KiB UTF-8, not blank). The flat message is never posted, and the strict protocol would reject it. A message whose tab is not active or whose epoch is not the shown document is ignored. |
| LNK-2 | Middle click on a link | *Unverified.* `NewWindowRequested` is not handled, so WebView2 opens its own popup window with the link. | Nothing opens: the adapter cancels `auxclick` on links, and `NewWindowRequested` is always handled. No new tab (.NET opens none either). |
| LNK-3 | Back and forward | `HistoryEntry.ScrollPosition` is always 0; the entry's document is re-rendered in the tab and scrolled to its fragment or the top. | The entry keeps the document's last reported scroll offset (the adapter reports it after scrolling settles and before following a link). Back and forward restore that offset, else the fragment, else the top. An entry in the same document only scrolls (CHROME-4). The mouse back and forward buttons step the history: over the page (the adapter cancels buttons 3 and 4 and posts `historyStep`) and over the shell (`WM_XBUTTONUP`, `WM_APPCOMMAND` `APPCOMMAND_BROWSER_BACKWARD`/`FORWARD`); two steps within 250 ms are one press. *Unverified* for .NET: WebView2's own back on those buttons. |
| LNK-4 | An anchor link to the anchor already current | `locationChanged` is false: nothing happens (no scroll). | The page scrolls to the anchor again (as a browser does); no history entry is added. |
| LNK-5 | `ftp:` and `tel:` links | Launched. | Blocked with `Blocked unsafe link destination.` (error). `http:`, `https:` and `mailto:` go to `ShellExecuteExW` with the `open` verb, no class override, on a worker thread; a failure shows `The link could not be opened: <error>`. |
| LNK-6 | Showing the target | `PrepareWebViewAsync` on the tab's own WebView2 (`NavigateToString`). | The tab's controller is reused: `WebViewHost::rebind_document` swaps the served document, removes the old adapters, registers the new ones and navigates in place, so the old page stays painted until the new one commits and no controller is created (measured: 105 to 234 ms to `NavigationCompleted` in place, against 411 to 762 ms for a new controller). Only the pinned navigation's id counts as loaded or failed. The same path now serves reloads, which closes the CHROME-14 gap (a reload no longer re-creates the controller; the anchor is restored as before), and CHROME-4's note that link navigation is not wired no longer applies. If the render fails, the previous location and tab name return and `Unable to open document: <error>` shows; the history is unchanged. |
| LNK-7 | A navigation that the adapter did not intercept (script failure) | *Unverified.* | Every navigation away from the pinned document is still cancelled. A user-initiated one is followed like a click: a URI on the document's origin is read as relative to the current document (the page's `<base href>` is the origin root, so root-relative and `..` forms cannot be told apart and resolve against the current folder); any other URI is resolved as an external link under the same policy. |
| LNK-8 | Hovering or focusing a link | *Unverified.* WebView2's status bubble shows the raw URL. | WebView2's status bubble is turned off (`IsStatusBarEnabled = false`); it would show the internal virtual-origin URL. The shell's status bar shows the resolved target: the path relative to the repository with its anchor, `<file>#<anchor>` for an anchor, the external URI, or the reason a link is blocked. The text is computed lexically (no file probe) and cleared when the tab changes or a link is followed. |
| LNK-9 | File probe | `File.Exists` on the combined path. | `probe_document_file` (worker thread only): the path passes the document path gate and opens for attributes with identification-only QoS as a regular disk file. With the sandbox enforced, the opened file's final path must also lie inside the repository root's final path (`GetFinalPathNameByHandleW`, ASCII-only case fold), so a junction or symbolic link inside the repository that leads outside it reads as a missing file. A UNC repository root cannot be checked lexically (`CanonicalPath`), so with the sandbox enforced its links are blocked with `Access blocked: Repository root is invalid; cannot enforce repository sandbox.` |

## Rationale

* The adapter keeps the frozen page bytes and the strict, identity-bound protocol; it follows the find adapter pattern already approved (FIND-5).
* Reusing the controller is what .NET does, and it is the main cost of a click: the measured in-place navigation is three to five times faster than a new controller and avoids a blank frame.
* Scroll restoration, the repeated anchor scroll and the mouse buttons make link browsing behave like a web browser, which the owner asked for (2026-11-07).
* LNK-5, LNK-7 and LNK-9 fail closed.
