# Portable updater: signed manifest, side-by-side staging, health-checked activation

Status: **approved — owner decision 2026-11-07**

Scope: `crates/marknexia-update` (all of it), `crates/marknexia-webview` (`bootstrap.rs` `DownloadUrl::parse_with_hosts` and `is_expected_publisher`, `bootstrap_native.rs` `verify_publisher` and `WinHttpDownloader::with_agent`), and `crates/marknexia-win32` (`window/update_native.rs`, `window/chrome/updater.rs`, the `update:` hooks in `window.rs`, the Help menu in `window/toolbar.rs`, and the update dialogs in `window/dialogs.rs`). The contract is `docs/superpowers/specs/2026-09-12-rust-update-contract-decision.md` (`update-manifest-v1`). The .NET source is `src/Marknexia.Infrastructure/UpdateService.cs` and `MainWindow.CheckForUpdates_Click`. Owner gate G2 (2026-11-06): build the updater with throwaway TEST keys only; the owner creates the release key outside the repository.

Evidence class: implemented, compiled and headless-tested (`crates/marknexia-update/tests`: `manifest.rs`, `archive.rs`, `stage.rs`, `activation.rs`, `check.rs`, plus unit tests; in-memory fakes for the network, Authenticode, process start and the clock; payloads are text files; the five frozen `compat/fixtures/v1/update-archives` cases are checked to hold no PE data and are rejected before extraction). The WinHTTP fetcher, `WinVerifyTrust` publisher check, owner-only folders, MSIX identity check, nonce source and the real health check of a launched shell have **not** run against a server or a signed release: no release key, manifest or signed payload exists (G2). The native gate `check_for_updates_reports_an_unconfigured_build` in `crates/marknexia-win32/tests/native_chrome.rs` is written but needs an interactive desktop. ARM64 is not tested.

## .NET behavior (read from the source, not observed)

`CheckAsync` queries `https://api.github.com/repos/ramanacr/marknexia/releases/latest`, ignores drafts and pre-releases, strips a `v` prefix and a `-suffix`, and compares with `System.Version`. The portable asset is `Marknexia-v{version}-win-{x64|arm64}.zip` with a `.sha256` file from the same release. Download follows at most 4 redirects to `github.com`, `api.github.com`, `objects.githubusercontent.com` or `release-assets.githubusercontent.com` (HTTPS, default port), with a 30 s client timeout and a 1,000,000,000-byte limit. The archive is written to `%LOCALAPPDATA%\Marknexia\Updates\pending-<guid>\package.zip`, its SHA-256 compared with the checksum file, extracted with traversal and size checks, and the four files `Marknexia.App.exe`, `Marknexia.App.dll`, `Marknexia.App.pri`, `marknexia-sbom.spdx.json` must exist. A hidden PowerShell script then stops the app, backs up the install folder, copies the payload over it with retries, and restarts. Errors appear as `Update check unavailable: <message>` or `Update could not be installed: <message>` warnings. A packaged (MSIX) process shows the update dialog with a "managed as an MSIX package" text.

## Observable differences

| ID | Condition | .NET oracle | Rust target |
| --- | --- | --- | --- |
| UPD-1 | Source of truth | GitHub release metadata and a `.sha256` file from the same release (no signature). | `update-manifest-v1.json` and the detached `update-manifest-v1.json.ed25519` from a build-time URL. The signature (Ed25519, embedded public keys, no unsigned fallback) is checked before the manifest is parsed. The manifest must be RFC 8785 canonical JSON: duplicate or unknown fields, white space, a byte-order mark, key order changes, noncanonical numbers and unknown algorithms or key ids are refused. The signature binds every field: version, channel `portable`, architecture, URL, SHA-256, byte length, minimum OS build, `artifactId` and `artifactKind`. The signature document is canonical JSON too: `{"algorithm":"Ed25519","keyId":"…","signature":"<128 lower-case hex>"}` (the contract fixed no encoding; lower-case hex has one spelling). |
| UPD-2 | Default build | Always contacts GitHub. | No URL, key or host is configured, so nothing is contacted. Help > Check for updates shows the warning `Update check unavailable: Updates are not configured for this build.` A build that would trust only the committed TEST key (or the TEST key with others, under any id) is also "not configured". |
| UPD-3 | MSIX / Store | The check runs; the dialog says the installation is managed as an MSIX package. | The menu item is grayed for a process with a package identity (`GetCurrentPackageFullName`). A command that arrives anyway shows `Update check unavailable: This installation is managed as an MSIX package; use the official release page or Store channel to update it.` The portable updater never runs, recovers or forwards in a packaged process and never touches Store-managed files. |
| UPD-4 | Update available | `Marknexia update available`: `Version X is available. Marknexia will verify the release signature and checksum, install it safely, and restart.` No `Open release page` (the manifest has no release page). There is no "no installable package" variant: a manifest is per architecture, and another architecture's manifest is an error. |

A version lower than the highest version already seen in a verified manifest (`Updates\highest-seen.json`, raised by every verified newer manifest, never lowered) is refused with `The update information is older than a release Marknexia has already seen, so it was not used.` (see UPD-14). |
| UPD-6 | Messages | Exception messages. | Kept from .NET: `The downloaded update checksum does not match.`, `The update archive contains a path traversal entry.`, `The update archive contains an invalid path.`, `The update archive is larger than the supported limit.`, `The update package is missing required file '…'.`, `Update download host is not trusted.`, `The update server returned too many redirects.`, `The update package is larger than the supported limit.` New: `The update information is not valid or is not signed for this build.`, `The latest version needs a newer version of Windows.`, `The downloaded update does not have the length its manifest declares.`, `The update archive contains duplicate entries.`, `The update archive contains a link.`, `The update archive is damaged or uses an unsupported format.`, `The update package contains an unexpected executable '…'.`, `The update file '…' failed verification: …`, `The update download was interrupted.`, and the rollback reasons (`… did not confirm that it works within 60 seconds; the previous version was kept.` and others in `activation::HealthFailure`). |
| UPD-7 | Limits | 1,000,000,000-byte download streamed to a file; 1 MiB checksum file; 30 s client timeout; 4 redirects. | The artifact is held in memory, bounded by the signed `byteLength` (at most 256 MiB), and must match it exactly before the hash; manifest 8 KiB, signature 1 KiB. WinHTTP: TLS 1.2 or later, system proxy, 15 s resolve and connect, 30 s send and receive, 300 s overall, 5 redirects, each to an exact allowlisted host. ZIP: 4,096 entries, 256 MiB per entry, 1,000,000,000 bytes in total (.NET value), names up to 240 bytes and 16 levels. |
| UPD-8 | Archive rules | Backslashes are separators; empty names are skipped; extraction first, then the required-file check. | Every entry is checked before anything is written. Also refused: backslashes, empty, `.` or empty segments, Windows-invalid characters, device names (`CON`, `PRN`, `AUX`, `NUL`, `CONIN$`, `CONOUT$`, `COM0`–`COM9`, `LPT0`–`LPT9` and the superscript forms `COM¹`–`COM³`, `LPT¹`–`LPT³`, with any extension), trailing dots or spaces, duplicates (case folded) and file/folder conflicts, Unix links and reparse points, encryption, ZIP64, multi-disk, methods other than stored and deflate, non-ASCII names without the UTF-8 flag, prepended or trailing data, overlapping entries, size or CRC-32 mismatches, any entry outside the exact payload file set (UPD-9; so no `.local`, `.manifest` or `.config` redirection files and no extra folders), and any executable (`.exe`, `.dll`, scripts, shortcuts, installers: `payload::EXECUTABLE_EXTENSIONS`) other than the allowed ones at the root. |
| UPD-9 | Payload | The four .NET files. | Exactly `marknexia-win32.exe` and `WebView2Loader.dll` (required) plus `README.txt` and `THIRD-PARTY-NOTICES.txt` (optional): any other file or folder is refused (`The update package contains an unexpected file '…'.`). Each staged executable must have the running architecture's PE machine and pass `WinVerifyTrust` (whole-chain revocation, no UI) through a handle that denies writers and deleters, with an explicit code-signing usage. The shell's publisher is pinned: the SHA-256 thumbprint of its leaf certificate (DER) must be in the build-time allowlist `MARKNEXIA_UPDATE_PUBLISHER_SHA256`, and its leaf name must also equal `MARKNEXIA_UPDATE_PUBLISHER` (an extra check, not the identity). The loader must pass the Microsoft policy (Microsoft root, as in WV2-4). Hash and Authenticode are both mandatory. |
| UPD-10 | Staging | `Updates\pending-<guid>\payload`, inherited DACL, deleted on failure. | `Updates\staging\pending-<random>` with a protected owner-only DACL (`D:P(A;OICI;FA;;;OW)`, also on `Updates`, `staging` and `versions`), files created new, then renamed to `Updates\versions\<version>-<arch>`. An existing `Updates` folder (for example one the .NET updater left) is refused when it is a reparse point or owned by another account, and otherwise re-secured with that DACL before use. Failure removes the pending folder; other stale stages are kept (fixture `stale-stage-cleanup`). |
| UPD-11 | Activation | PowerShell copies the payload over the install folder (with a backup) and restarts; no health check. | Side by side: `transaction.json` records the previous pointer and the nonce's SHA-256, `active.json` switches atomically, and the new shell starts with `--post-update-health <nonce>`. It acknowledges in `Updates\health\ack-<pid>.json` only when its window is visible, WebView2 is ready and the bundled offline welcome document rendered, and only if the transaction names its own payload and the nonce matches. The old shell waits at most 60 s from the launch; a valid acknowledgement from the launched, still-running process commits, and the old shell closes. A timeout, crash or exit, wrong nonce or process, failed probe or launch failure ends the new process, restores the previous pointer (or removes it when there was none), deletes the failed payload, writes `last-update-failure.json`, and shows `Update could not be installed: …`. The unpacked installation is never modified and the previous payload is kept until the next successful update. No PowerShell, no elevation. The transaction binds the coordinator to its process id **and creation time**, so a reused id does not block recovery. When the old window closes during the health wait, recovery restores the previous pointer but keeps the candidate's payload while its shell still runs. **Deviation from the contract:** the contract asks for the nonce "through a protected local channel"; the nonce is passed on the command line (`--post-update-health <nonce>`), readable by processes of the same user. Only its SHA-256 is stored, the acknowledgement must come from the launched process id, and the update folders are owner-only. Task 8 must accept this or require a private channel (for example an inherited anonymous pipe). |
| UPD-12 | Starting the shell | Not applicable. | A normal start forwards only when all hold: the build has a configured channel (default builds never forward or recover); the process is not packaged and **not elevated** (`TokenElevation`), so running Marknexia as administrator never starts a payload; the `Updates` folder is not a reparse point, is owned by the current user and has a protected DACL that grants only the user (or OWNER RIGHTS). It then resolves an interrupted transaction (rolled back unless its coordinator, same id and creation time, still runs) and, when `active.json` names a newer payload whose shell exists and whose version matches the payload id, opens that shell with a handle that denies writers and deleters, checks its PE machine and the pinned publisher (UPD-9) through that handle, and starts it with the same arguments while the handle is still open. A planted or unsigned payload, an invalid pointer, a pointer outside `versions` or a missing shell runs the started executable. Health mode skips the single-instance hand-off and opens no documents; after the old version closes, the new one runs without being the single-instance primary until its next start. |
| UPD-13 | Configuration | Hard-coded GitHub endpoint and hosts. | Build-time only (`option_env!`): `MARKNEXIA_UPDATE_MANIFEST_URL` (`{arch}` is replaced by `x64` or `arm64`), `MARKNEXIA_UPDATE_ALLOWED_HOSTS` (exact host names), `MARKNEXIA_UPDATE_PUBLISHER`, `MARKNEXIA_UPDATE_PUBLISHER_SHA256` (certificate thumbprints, required), `MARKNEXIA_UPDATE_PUBLIC_KEYS` (`keyId=<64 hex>`, public keys only; noncanonical and small-order keys are refused). Unset keys mean the committed TEST key. |
| UPD-14 | Freeze and replay | Not applicable (GitHub serves the latest release). | `update-manifest-v1` has no expiry: a mirror or attacker that keeps serving an old, validly signed manifest can freeze an installation on that version (it is never offered a newer one), and cannot be told apart from "no new release". The highest-seen floor (UPD-5) stops a partial replay from offering an older version once a newer one was seen, but not a freeze. **Proposed for `update-manifest-v2`:** a signed `expires` timestamp (UTC, RFC 3339); a manifest past it is refused and the user sees that update information is out of date. |

## Release key path (owner)

1. Create the Ed25519 release key outside the repository and keep the private key offline. Never commit it.
2. At release build time set `MARKNEXIA_UPDATE_PUBLIC_KEYS=<keyId>=<public key, 64 lower-case hex>` (several keys: comma-separated, for rotation), `MARKNEXIA_UPDATE_MANIFEST_URL`, `MARKNEXIA_UPDATE_ALLOWED_HOSTS`, `MARKNEXIA_UPDATE_PUBLISHER` and `MARKNEXIA_UPDATE_PUBLISHER_SHA256` (the SHA-256 of the signing certificate's DER; add the renewal certificate before a renewal). Cargo rebuilds `marknexia-update` when they change.
3. For each architecture, publish the canonical manifest bytes (`ManifestDocument::to_canonical_json`) and the signature document (`SignatureDocument::new(keyId, signature).to_canonical_json()`), signing the manifest bytes exactly as published.
4. The committed TEST key (`keys::TEST_KEY_ID`, public key `keys::TEST_PUBLIC_KEY_HEX`, seed in `crates/marknexia-update/tests/support/mod.rs`) is public on purpose and is refused as a release key.

## Security notes

* Trust needs the Ed25519 signature, the SHA-256 and byte length from the signed manifest, and Authenticode on every staged executable. The host allowlist, size bounds and archive rules limit what is fetched and written but are not trust decisions on their own.
* The nonce travels on the command line, which other processes of the same user can read. On disk only its SHA-256 is stored; the acknowledgement must also come from the launched process id, and the update folders are owner-only. A same-user process could plant files in the user's folders; that is why a normal start never trusts the pointer alone: it forwards only in a configured, unelevated process, through a private folder, and only to a shell whose pinned signature and PE machine are verified on a locked handle (UPD-12). A medium-integrity process therefore cannot use the pointer to run code in an elevated Marknexia.
* The release publisher's identity is its certificate thumbprint, not its name: a look-alike certificate with the same subject name is refused.
* Revocation fails open when offline (the Authenticode default), as in WV2-4.
* The download is in memory: a 256 MiB bound keeps the peak memory bounded.

## Rollback

Remove the `update:` hooks in `window.rs`, the `CheckForUpdates` command and the menu item. Existing `Updates\versions` folders then stay unused; delete `Updates\active.json` to stop forwarding.
